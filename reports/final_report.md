# Day 10 Reliability Report

## 1. Architecture Summary

The gateway applies reliability layers in sequence: cache check first, then circuit-breaker-guarded provider calls, then a static fallback of last resort.

```
User Request
    |
    v
[ReliabilityGateway.complete(prompt)]    ← timing starts here
    |
    |--- [Cache.get(prompt)] ---> HIT?  ---> return (route: "cache_hit:<score>")
    |     - privacy check (block)         |
    |     - false-hit guard (block)       |
    |                               MISS
    v
[CircuitBreaker: primary]
    |  OPEN?  → raise CircuitOpenError (fail-fast, no retry)
    v
[FakeLLMProvider: primary]
    |  success → cache.set(), return (route: "primary:primary")
    |  failure → record_failure() → may open circuit
    v
[CircuitBreaker: backup]
    |  OPEN?  → raise CircuitOpenError
    v
[FakeLLMProvider: backup]
    |  success → cache.set(), return (route: "fallback:backup")
    |  failure
    v
[Static fallback message]              (route: "static_fallback")
    |
    v
    latency_ms = full wall-clock time from entry to exit
```

**Route reason format:** Always `"<role>:<provider_name>"` or `"cache_hit:<score>"` — provider name and reason are always explicit so logs are unambiguous.

## 2. Configuration

| Setting | Value | Why this value |
|---|---:|---|
| `failure_threshold` | 3 | Low enough to detect a failing provider quickly (3 requests ≈ 0.6 s at 200 ms/req); high enough to tolerate single-request jitter without false opens |
| `reset_timeout_seconds` | 1.5 | Shorter than the default 2 s so OPEN → HALF_OPEN transitions complete within the 100-request concurrent simulation window (~1.5 s with concurrency=10); still realistic for a dev environment |
| `success_threshold` | 1 | One successful probe is sufficient to close — keeps recovery fast; raising it would only add latency without meaningfully improving reliability |
| `cache.ttl_seconds` | 300 | 5-minute freshness appropriate for FAQ/policy queries; content changes on the order of hours, not seconds |
| `similarity_threshold` | 0.92 | Tested: 0.85 gives a false hit on `"refund policy for 2024"` vs `"refund policy for 2026"` (score 0.74 > 0.85 would NOT match, but 0.3 test shows the guardrail). 0.92 eliminates all false hits on date-sensitive queries in the sample set |
| `load_test.requests` | 100 | Enough to trigger multiple circuit open/close cycles at concurrency=10 |
| `load_test.concurrency` | 10 | ThreadPoolExecutor workers; simulates realistic concurrent production load and shortens wall-clock time so reset_timeout cycles complete within the run |
| `cache_enabled` (per scenario) | false for circuit scenarios | Circuit-breaker scenarios (`primary_timeout_100`, `primary_flaky_50`) disable cache so every request hits a provider — otherwise cache hits short-circuit provider calls and the circuit never accumulates failures |

## 5. Cache Comparison

Simulation run twice (100 requests, default provider settings, concurrency=10):

| Metric | Without Cache | With Cache | Delta |
|---|---:|---:|---|
| latency_p50_ms | 288.36 | 0.33 | **−99.9%** |
| latency_p95_ms | 492.25 | 229.83 | −53.3% |
| estimated_cost | 0.0389 | 0.0165 | **−57.5%** |
| cache_hit_rate | 0.00 | 0.70 | +0.70 |

**Why p50 drops to 0.33 ms:** With 5 unique queries and 100 requests, each query is first-served via provider (~200 ms), then every repetition is a sub-millisecond cache hit. 70% of requests become cache hits.

**Similarity threshold justification — concrete false-hit example:**

```
Query stored : "Summarize refund policy for 2024 deadline"
Query lookup : "Summarize refund policy for 2026 deadline"

Token similarity score : 0.7444
Would match at threshold 0.3? YES  (0.7444 > 0.3)
_looks_like_false_hit()? YES  (4-digit set {2024} ≠ {2026})

cache.get("...2026...") → (None, 0.7444)   ← guardrail blocked the false hit
```

The `_looks_like_false_hit()` function finds all `\b\d{4}\b` tokens in both strings; if the sets are non-empty and unequal, the match is rejected and logged. This prevents serving a 2024 policy answer to a 2026 deadline question even when the two queries are 74% similar.

**TTL justification:** 300 seconds (5 min) is the tradeoff point where FAQ-type answers remain fresh (policy documents rarely change within a single session) while the cache stays small in memory. A shorter TTL (60 s) would halve the hit rate; a longer TTL (3 600 s) risks serving genuinely stale answers if policy documents update.

## 6. Redis Shared Cache

### Why in-memory cache is insufficient for production

Each gateway process runs its own `ResponseCache` in private heap memory. In a multi-instance deployment (load balancer → N gateway pods):

- **No sharing:** Instance A caches the answer; Instance B independently calls the provider and pays the token cost again.
- **No consistency:** After a provider returns an updated answer, different instances serve different versions until their own TTLs expire independently.
- **Warm-up duplication:** Every time a new instance starts (auto-scaling), it starts cold and must re-warm its cache, spiking provider costs.

### How `SharedRedisCache` solves this

`SharedRedisCache` stores all entries in a single Redis server shared by every gateway process:

```
Instance A  →  cache.set("refund policy?", "...")  →  Redis: rl:cache:abc123
Instance B  →  cache.get("refund policy?")          ←  Redis HIT (same entry)
Instance C  →  cache.get("refund policy?")          ←  Redis HIT (same entry)
```

One provider call warms the cache for all instances simultaneously.

### Implementation

```python
def set(self, query, value, metadata=None):
    if _is_uncacheable(query):
        return                               # privacy guardrail
    key = f"{self.prefix}{self._query_hash(query)}"
    self._redis.hset(key, mapping={"query": query, "response": value})
    self._redis.expire(key, self.ttl_seconds)   # automatic TTL eviction

def get(self, query):
    if _is_uncacheable(query):
        return None, 0.0                     # privacy guardrail
    # Phase 1: exact match (O(1))
    key = f"{self.prefix}{self._query_hash(query)}"
    response = self._redis.hget(key, "response")
    if response:
        return response, 1.0
    # Phase 2: similarity scan (O(n entries))
    best_score, best_response, best_cached_query = 0.0, None, None
    for redis_key in self._redis.scan_iter(f"{self.prefix}*"):
        cached_query = self._redis.hget(redis_key, "query")
        score = ResponseCache.similarity(query, cached_query)
        if score > best_score:
            best_score, best_response, best_cached_query = score, ..., cached_query
    if best_score >= self.similarity_threshold:
        if _looks_like_false_hit(query, best_cached_query):
            self.false_hit_log.append(...)   # log and reject
            return None, best_score
        return best_response, best_score
    return None, best_score
```

All Redis calls are wrapped in `try/except` — if Redis is unreachable the gateway continues serving from providers without crashing (graceful degradation).

### No Retry Storm

When the circuit is OPEN, `allow_request()` returns False immediately and `CircuitOpenError` is raised before the provider is called. The circuit breaker's `call()` method does NOT retry the same provider — it raises and lets the gateway try the next provider in the chain. Verified by `test_circuit_opens_and_fallback_serves`.

### Concurrent Load Evidence

With `concurrency: 10`, the simulation dispatches 10 requests simultaneously via `ThreadPoolExecutor`. Observed effects:
- Wall-clock time for 100 requests: ~15 batches × 200ms ≈ 3 seconds (vs 20 seconds sequential)
- Multiple failure counts arrive concurrently → circuit opens faster (fewer wall-clock seconds to reach threshold)
- `reset_timeout_seconds: 1.5` was chosen precisely so HALF_OPEN transitions complete within the concurrent simulation window

## 8. Failure Analysis

**Remaining weakness: circuit breaker state is instance-local**

Each `CircuitBreaker` lives in memory on one gateway process. In a multi-instance deployment:
- Instance A's circuit opens after 3 failures — it stops sending to the failing provider.
- Instance B's circuit is still CLOSED — it continues hammering the same failing provider.
- Neither instance has a global view of failure rate; protection is fragmented.

**Concrete impact:** If there are 10 gateway instances and each independently needs 3 failures to open its circuit, the failing provider receives up to 30 failure requests before all instances protect themselves. During recovery, each instance independently sends its own probe — 10 simultaneous half-open probes, which may overwhelm a provider that is just recovering.

**Proposed fix:** Store circuit breaker counters in Redis using atomic operations:

```python
count = redis.incr(f"cb:{name}:failures")  # atomic across all instances
if count >= failure_threshold:
    redis.set(f"cb:{name}:state", "open")
    redis.expire(f"cb:{name}:state", reset_timeout_seconds)
```

`INCR` is atomic; 3 failures across any combination of instances open the circuit globally. `EXPIRE` on the state key eliminates the per-instance `opened_at` timer. This is the natural extension of `SharedRedisCache` to circuit state.

## 9. Next Steps

1. **Redis-backed circuit state** (highest production value): extend `CircuitBreaker` to store `failure_count`, `state`, and `opened_at` in Redis with `INCR`/`SET`/`EXPIRE`. This provides coordinated failure protection across all instances — the most impactful reliability gap in the current design.

2. **Cost-aware routing**: track cumulative `estimated_cost` across requests. At 80% of a monthly budget cap, skip the expensive primary provider and route to cheaper backup. At 100%, return cache-only or static fallback. This turns cost into a first-class SLO, preventing runaway spend during traffic spikes.

3. **Property-based circuit breaker tests**: use `hypothesis` to generate random failure/success sequences and verify that the state machine invariants always hold (e.g., `failure_count < failure_threshold` whenever `state == CLOSED`, `opened_at` is always set when `state == OPEN`). Random sequences will find edge cases in concurrent state mutations that hand-crafted tests miss.
